# Limeghost repository guidance

Use [AGENTS.md](AGENTS.md) as the authoritative development instruction file. Read both [docs/limeghost-strategy.md](docs/limeghost-strategy.md) and [docs/project-context.md](docs/project-context.md) before proposing or implementing product-direction changes.

Essential constraints:

- The current installed product is a standalone, macOS-first SwiftUI + WebKit browser for ordinary users.
- Do not switch the current product to Chromium. The isolated CEF scaffold is only a future cross-platform/extension gate; it is not linked into the app and is not a full Chromium source fork.
- The root browser extension is a retained validation artifact, not the primary deliverable.
- Page assistance is local-first. Limeghost holds no API key and calls no model.
- The assistant panel (`AICompanion`, ⇧⌘A) is the person's own ChatGPT, Claude, Gemini, Le Chat or Grok in a web view, on their own account. **Never type into it, never press its send button, never read what it says.** Scripting a provider's page is automated access to a service Limeghost has no agreement with, which their consumer terms forbid; the person pastes and sends. Compare answers is two manual pastes for exactly this reason — never wire one input box to both columns. A link clicked inside it opens in a tab, because navigating the panel away is how a conversation is lost.
- The assistant panel must stay **one** `AICompanionPanel` in one place in the view tree, resized rather than moved between layout branches. `WebView` hands SwiftUI a web view the session owns, so moving the panel between branches is a destroy-and-rebuild that reattaches the assistant that already existed and orphans one created in the same update — which is how Compare first shipped showing a header above a blank rectangle. For the same reason, key a `WebView` on `session.instanceID` and never on `ObjectIdentifier(session)`: an address is reused after a free, and park-and-restore frees and rebuilds sessions for the same assistant.
- Panel controls (Compare, Fill the window) sit **immediately left of the close button and nowhere else**, so they cannot move: close is anchored to the window's own right edge in every layout. They lived in the primary column's header once, which slides a thousand points inward when a second column opens, so they appeared to wander off. Both fold away while comparing, because neither has a job there — the window is already filled and the way back is closing a column — which leaves two identical headers.
- **Every close button closes its own column, and the last one closes the panel.** Never add a button inside the panel that closes more than the column it sits on: two identical glyphs a thousand points apart doing different amounts of damage is how a conversation gets lost. The window-level "close it all" is the toolbar button and ⇧⌘A, which is where a window-level control belongs. Closing one of two promotes the survivor, remembers it, and reloads nothing.
- Compare tops out at **two** assistants, and this is a judgment, not a limit waiting to be raised — three or more was rejected on August 31, 2026 with the reasoning in [docs/project-context.md](docs/project-context.md). Two answers side by side is a comparison; three is a vote, and models that share training data share failure modes, so a majority among them is false confidence of exactly the kind this product deleted a feature to avoid. `AICompanion.companionWidth` (500) is a judgment too: it is below the ~640-point breakpoint where providers show their own sidebar, which suits a side panel, but the per-provider breakpoints have never been measured. Do not defend 500 as evidenced.
- Compare fills the window on purpose, not because two columns and a page cannot fit — on a 2560-point display they can. It is a focused task: you are reading two answers and deciding between them, and the page is either irrelevant (a question from your head) or already copied into both. Do not "reclaim" that space. Closing one column is the way back to an assistant beside the page.
- One rule governs the assistant's layout: **if the person asks for a page, the page becomes visible; nothing moves when they did not ask.** Every door that opens a page calls `BrowserWorkspace.makeRoomForPage()` — ⌘T, a link from the assistant, the address bar, a bookmark, Library/History rows, reopening a closed tab, the bookmarks and history homes, the Home button, an AI-guide card, back/forward, a local file, a URL from another app. Deliberately excluded: selecting a tab that already exists, a provider's sign-in popup, and reload — none is a request for a *different* page. There is no single choke point, because "somebody asked" cannot be told from "the page redirected itself" without an explicit signal; `testEveryWayOfAskingForAPageUncoversIt` is what stops a new door forgetting, so add a row to it whenever you add one. It half-shipped once — ⌘T stepped aside and nine other doors did not — and an inconsistent rule is worse than either whole one.
- Where a window is too narrow to show a page and the assistant at once, stepping aside means **leaving**, not shrinking: shrinking reveals nothing there. The assistant returns by itself when the window widens, and the lit toolbar button is the advertised way back — never a keyboard shortcut, which the audience does not know. An assistant closed by hand must **not** come back when the window widens; only `hiddenBecauseThereWasNoRoom` reverses.
- Rank assistants by which one stayed **on screen**, never by what was read. Limeghost does not know what anybody read and must never imply it does, in code, comments, or interface.
- The companion keeps at most `AICompanion.maximumLiveSessions` (2) web views loaded: the visible assistant and the most recently used hidden one. A hidden `WKWebView` does not release its memory — WebKit holds a "recently visible" claim for four minutes and suspension pauses rather than discards — so the cap is what stops every assistant somebody tried from staying resident. Do not raise it without measuring. Dropping one parks its conversation URL and reopens it on return; drafts and temporary chats do not survive, and the interface must not imply they do.
- Analyze Page extracts a page's readable text and checks it for visible risk signals. It does not summarize, rank, or judge what the page says, and must never be described as doing so — that layer was removed on August 30, 2026 for the reasons recorded in [docs/project-context.md](docs/project-context.md). Extraction preserves the source language. Risk phrases are deterministic and have narrower language coverage than extraction; never imply parity.
- The AI home is a curated local directory of official links. Its sparse task badges, broad access labels, checked date, and source links follow [docs/ai-catalog-editorial.md](docs/ai-catalog-editorial.md); they are not universal/live rankings, Limeghost testing, partnerships, exact prices, affiliate ordering, or automatic page/prompt sharing.
- Never sell browsing history, add hidden ads, invent partnerships, or market heuristic risk signals as security verdicts.
- Prioritize extraction quality, measured calm performance, real-user clarity, and release security before broad feature expansion or monetization. Extraction is now the whole of the local pipeline; anything added later reads what it produces, so its quality bounds everything.
- The primary promise is “Limeghost makes the AI world simple for ordinary people.” Optimize the first minute around a human task, a small set of useful AI paths, and a page whose text is ready to hand to an AI. Limeghost prepares a page; it does not interpret one. Do not present page understanding as delivered.
- Favor founder-led demos, real early testers, honest before/after examples, GitHub build notes, and observed learning. Do not recommend spam, fake traction, premature paid ads, or guaranteed-growth claims.
- Use [docs/go-to-market.md](docs/go-to-market.md) for launch decisions: the brand is global and English-first, while the first validation wedge is creators overwhelmed by AI. Treat activation, seven-day retention, and voluntary referrals as stronger evidence than views or follower counts.
- Preserve the `LimeghostCore` versus macOS UI/WebKit boundary and document material behavior or data-flow changes.
- Do not claim production signing, notarization, App Store readiness, password security, or security review without evidence.
- The Swift and JavaScript local-analysis implementations are intentionally separate but behaviorally equivalent. `macos/LimeghostBrowser/Tests/LimeghostCoreTests/Fixtures/local-analysis-contract.json` and `provider-contract.json` are the single source of truth for both, read by Swift through `Bundle.module` and by Node through a relative path. Change behavior in the contract first, then make both runtimes satisfy it; never edit one implementation alone.
- Never reintroduce word-frequency ranking of sentences. It was removed because it cannot know what matters: measured on a live Britannica page, the winning sentences were simply the ones packed with the page's most repeated words — `ai(54)`, `intelligence(27)`, `artificial(22)` — and the site's own navigation menu scored second highest. Deciding which sentences matter requires a model that reads. Arithmetic over word counts is not that, and no amount of tuning makes it one.
- `LocalAnalysisEngine.readableText` must never emit a character the page does not contain: it is what Copy for AI puts on somebody's clipboard, and it must be the page's own words. Sentence splitting must also stay identical in Swift and JavaScript — `segmentationCases` in the shared contract enforces that — because `repeatedInterfaceText` counts whole sentences, so a split that differs between runtimes silently disables the media-boilerplate filter in one of them. Recognised sentence terminators are `. ! ? 。 ！ ？ । ॥ ۔ ؟ ։` — a script whose terminator is missing reads as one endless sentence and its pages look unpunctuated to structure detection. Thai is still not covered: it marks sentences with spaces and has no terminator to recognise. A full stop is not a boundary before a lowercase letter or a digit, after a lone initial, or after an abbreviation listed for the page's language in `sentenceAbbreviations`/`SENTENCE_ABBREVIATIONS_BY_LANGUAGE` — never merge those per-language lists, because Italian `es.` abbreviates *esempio* while Spanish `es` is the verb. Keep the Swift and JavaScript digit, letter and case tests equivalent and count graphemes on both sides, or the same sentence splits differently in each. `Character.isNumber` ↔ `\p{N}`; `Character.isLowercase` ↔ `\p{Lowercase}`, the binary property — **not** `\p{Ll}`, which is the general category alone and omits the ordinal indicators (`º`, `ª`) that ordinary Spanish and Portuguese prose uses, so `5.º` split in one runtime and not the other. Bound a term with `(?<![\p{L}\p{N}])…(?![\p{L}\p{N}])` and never with `\b`: JavaScript's `\b` is ASCII and finds no boundary after an accented letter, so `\bétude\b` and `\b(a déclaré)\b` match in Swift's ICU and never here.
- Risk heuristics must stay context-aware. A bare mention of remote-desktop software is ordinary technical writing; a signal requires nearby action language plus pressure, support, account, security, or payment context.
- The repository is licensed under AGPL-3.0 ([LICENSE](LICENSE), verbatim upstream text). Do not relicense, add per-file license headers, or change the SPDX identifier in `package.json` without explicit user direction. Contribution terms (CLA or DCO) are still undecided; accepting outside patches before that is settled would compromise the maintainer's ability to offer separate commercial terms.
- Tracker blocking is real and must stay honest. It compiles a curated first-party domain list ([docs/content-blocking.md](docs/content-blocking.md)) through WebKit's `WKContentRuleList`. WebKit cannot report what it blocked, so the UI shows state only — never add per-page or running block counts, never import third-party blocklists without a separate licensing review, and never present blocking as a safety verdict.
- The brand mark lives in `docs/brand/limeghost-mark-2026-08-31/` in three forms, and they are not interchangeable: **full** (ring, face and wing) at 32 px and above, **small** (the face alone) at 16–32 px, **mono** (black on transparent) wherever only one colour is available. `generate-app-icon.swift` reads the first two and switches between them by size — the full mark's ring turns to mud at 16 px and takes the face with it, which was measured rather than assumed. Do not make one drawing serve every size, and do not let a gradient approach the background colour: an earlier mark faded to near-black and lost the owl's whole body on Limeghost's own chrome. If the artwork is missing the script warns and falls back to the geometric frame mark rather than failing the build.
- **The storage identifiers keep the old name on purpose, and must not be "tidied".** The bundle identifier is `com.clearframe.browser`, profile suites are `com.clearframe.browser.profile.<uuid>`, and the eighteen preference keys are `clearframe.*`. They were deliberately left behind when the product was renamed to Limeghost on August 31, 2026, because they are one storage system and every one of them is invisible to users. `UserDefaults.standard` **and** `WKWebsiteDataStore.default()` are both keyed off the bundle identifier, so changing it orphans bookmarks, history, profiles *and every cookie and login* — WebKit exposes no API to migrate its store. Renaming them buys nothing and costs everything. If they ever must change (App Store submission is the only real reason), do all of them together, in one commit, with migration code that copies the old data forward and a test proving it, and move `~/Library/WebKit/com.clearframe.browser` on disk before WebKit initialises.
- All chrome and surface colors come from `LimeghostTheme` in the `LimeghostBrowser` target; do not reintroduce scattered color literals. Semantic status colors (risk green/orange/red, failed-download red) stay semantic and are not part of the brand accent family.
- Site icons follow the `FaviconStore` policy: fetched only during an actual visit, and only from the page's own origin or a host that page already loaded something from during the same visit — its own CDN, in practice. State the reach that way rather than as “the site's own address”: `/favicon.ico` follows redirects, so the address-only form was never exactly true, and a favicon service fails this test outright because no page ever loads anything from one. Cached locally, memory-only in private tabs, wiped by the browsing-data reset, never a third-party icon service; unvisited hosts fall back to the local identity-color square.
- Folder icons ship as three selectable sets. Whether a tint reaches one is decided by the artwork, not by policy: Limeghost's own 104 are drawn in `currentColor` and are the only tintable set; never bake a colour into it. Limeghost's set stays the default because it is the only one containing the plain folder that every unset folder falls back to. The licensed sets carry their own colours, so the tint row is hidden for them rather than shown doing nothing, and their attribution must stay visible in the picker. Do not add GPL-licensed icon sets: one was added and withdrawn on Aug 19, 2026 because GPL copyleft covers the whole program, not only adaptations of the artwork, which would end the option of separate commercial terms. Prefer CC BY. Stickies (100) is Streamline artwork under CC BY 4.0; its single-lime `duo` form was withdrawn because that green fought the mint accent, and folders saved with it migrate to the surviving drawing rather than resetting. Emoji (1261) is EmojiOne v1 under CC BY-**SA** 4.0: bundling it is a collection, not an adaptation, so it does not put the app under share-alike — but modifying that artwork would, which would compromise any separate commercial terms. Treat it as read-only, never merge it into Limeghost's own set, and regenerate rather than hand-edit: `StickiesIconCatalogData.swift` and `EmojiOneIconCatalogData*.swift` come from the matching `scripts/import-*-icons.py`. `LimeghostTheme.siteIconSize` is the single size for every site icon and folder mark, set to match the toolbar's own icon row.
- The full-page bookmarks home is a per-tab start surface. New tabs and the Home button always open the AI guide; ⌘⌥B and the bar's All Bookmarks affordances open the bookmarks home.
- Automated coverage is not user validation. No observed-user session has been run yet, so never describe activation, retention, or usability as validated.

Do not revive rejected paths from old prototypes or conversations without explicit user direction and evidence. The root [README](README.md#documentation-index) links the strategy, product, architecture, privacy, research, run, and release-gap documents. The trusted upstream is `https://github.com/romanlucian/Ki-browser`; never rewrite it casually.
